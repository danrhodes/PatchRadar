2. `tracker.md` is the live progress file. Update it after every task. Commit it with the code.
3. Work phases in order: P1, P2, P3, P4. Do not start P2 until every P1 acceptance test passes.

7. Never hardcode CSS class names from Microsoft pages. Locate content by heading text.

## 1. Purpose

Tray-only Windows tool. It lists recently installed Windows updates. It fetches each update's Microsoft KB article. It extracts **Improvements** and **Known issues**. It colour-codes each update by risk.

Primary use: an engineer sees a symptom on a machine, right-clicks the tray icon, and finds the update that introduced it.

Trigger case: KB5127648 (Oct 2026, Windows 11 24H2/25H2/26H2). Its **Improvements** section changes `BlockNtlmv1SSO` default from Audit (0) to Enforce (1). That breaks MS-CHAPv2-based Wi-Fi (802.1X/RADIUS), Ethernet and VPN. The change is listed under Improvements, not Known issues. The tool must flag it red.

Users: the author (L3 MSP engineer) and other MSP engineers. Personal tool, MIT licence, public GitHub repo.

## 4. Collecting installed updates

Goal: fastest reliable list. Target under 3 s.

1. **Primary: WUA history.** Late-bound COM, no interop assembly.
   ```csharp
   var t = Type.GetTypeFromProgID("Microsoft.Update.Session")!;
   dynamic session = Activator.CreateInstance(t)!;
   dynamic searcher = session.CreateUpdateSearcher();
   int total = searcher.GetTotalHistoryCount();
   dynamic history = searcher.QueryHistory(0, Math.Min(total, maxEntries));
   ```
   Per entry read: `Title`, `Date`, `ResultCode` (2 succeeded, 3 succeeded with errors, 4 failed, 5 aborted), `Operation` (1 install, 2 uninstall), `Categories`, `SupportUrl`, `UpdateIdentity.UpdateID`.
   Run on a background thread. Release COM objects.
2. **Secondary: `Win32_QuickFixEngineering`** (WMI via `System.Management`). Adds updates installed offline (MSU, DISM) that WUA history misses.
3. **KB extraction.** Regex `\(KB(\d{6,8})\)` on `Title`. Fallback `KB(\d{6,8})` anywhere.
4. **Merge and dedupe by KB.** Keep latest entry per KB. Track final state: Installed, Failed, Uninstalled.
5. **Filtering (all configurable, see section 8).**
   - History window: default 90 days. `0` = all.
   - Categories: default include Security/Cumulative, .NET, Servicing Stack, Drivers, Office, other. Default exclude Defender definition/security-intelligence updates (title regex `Security Intelligence Update|Definition Update`). Daily definition KBs create noise.
   - Failed installs: hidden by default, toggle to show.
6. **Menu cap.** Show newest 15 by default. Setting range 5–100. Full list lives in the All Updates window.

Interface for testing:
```csharp
public interface IUpdateHistoryProvider { Task<IReadOnlyList<InstalledUpdate>> GetAsync(CancellationToken ct); }
```

## 5. KB data: fetching and parsing

### 5.1 Sources (ordered chain, per KB)

| Order | Source | Purpose |
|---|---|---|
| A | `https://support.microsoft.com/help/<KB>` (follow redirects, store canonical URL) | Improvements + Known issues. Primary. |
| B | Windows release health (`learn.microsoft.com/windows/release-health/…`, per OS version and Server release) | Known issues with originating KB. Fallback and enrichment. Page layout **unverified**; capture fixtures first. |
| C | Hidden WebView2 render of source A | Fallback when A returns 403, a JS challenge or an empty shell. P3. Runtime may be absent on Servers; degrade gracefully. |

**Risk (verified):** an automated fetcher received a bot-detection block from `support.microsoft.com/help/5127648`. Plan for it.
- Send a standard browser User-Agent (configurable in settings), `Accept-Language: en-GB,en;q=0.9`.
- Max 2 concurrent requests. 500 ms minimum gap. Exponential backoff on 403/429/5xx.
- Honour cache. Never refetch inside TTL.
- On block: mark update **Unknown** (grey), try source B, then C if enabled. Log reason.
- Check Microsoft site terms for automated access (**unverified**). Keep request volume low.

Link shown to users: always `https://support.microsoft.com/help/<KB>`.

### 5.2 Parsing rules

Locate sections by heading text (case-insensitive, `h1`–`h3` or bold paragraph):
- `Highlights`
- `Improvements`
- `Known issues in this update` / `Known issues`
- `How to get this update` (ignore)

Walk sibling nodes after the heading until the next heading of same or higher level.

**Improvements:** each `li`/paragraph becomes `{ Category, Text, Links }`. `Category` = leading `[Text]` tag if present (example `[Authentication]`). Keep full text.

**Known issues:** parse tables with a Symptom column and a Workaround column. If no table, split on bold sub-headings or paragraphs containing `Workaround`. If structure unrecognised, store the raw section text as one issue. Never drop data.

**No issues:** regex `not currently aware of any issues` → zero issues, Green.

**Resolved issues:** text containing `Resolved`/`This issue has been resolved` → `Status = Resolved`. Shown in detail window. Not counted in severity.

**Non-standard pages** (OOB, .NET Framework, driver KBs): if no recognised headings, scan the full body text for keywords. Store the body text. Flag `Structure = Unknown`.

Also capture: `OSBuild` (regex `OS Build (\d+\.\d+)`), release date, `Applies to` text.

### 5.3 Behaviour-change detection (Improvements)

An improvement becomes a **BehaviourChange** when it matches both:
- a change phrase (default list in section 6.3), and
- at least one impact keyword (critical list).

Setting `treatBehaviourChangesAsIssues` default `true`. This deviates from "known issues only". Reason: KB5127648 hides its breaking change under Improvements.

### 5.4 Cache

Path: `%LOCALAPPDATA%\PatchRadar\cache\kb\<KB>.json`.
Fields: `kb`, `fetchedUtc`, `source`, `canonicalUrl`, `status`, `improvements[]`, `knownIssues[]`, `rawText`, `contentHash`.
Refresh policy (settings-configurable):
- Update installed ≤ 30 days ago: refresh every 12 h.
- Older: refresh every 7 days.
- Failed fetch: retry after 1 h, then 6 h, then 24 h.
Manual **Scan now** forces refresh for updates inside the 30-day window.

## 6. Severity engine

States: **Green**, **Orange**, **Red**, **Grey** (not yet fetched or fetch failed).

| State | Rule |
|---|---|
| Grey | No cached KB data, or fetch failed. |
| Green | KB parsed. No active known issues. No behaviour changes matching critical keywords. |
| Orange | At least one active known issue with no critical keyword match. |
| Red | At least one active known issue matching a critical keyword, or a BehaviourChange matching a critical keyword. |

Resolved issues do not count.

### 6.1 Keyword matching
Case-insensitive. Word-boundary match. Prefix `re:` = regex. Match against issue symptom + workaround text and improvement text. Record matched keywords per update. Show them as chips in the detail window.

### 6.2 Default critical keywords (editable)
```
RADIUS, 802.1X, 802.11, EAP, PEAP, MS-CHAP, MS-CHAPv2, NTLM, NTLMv1, Kerberos, NPS,
Wi-Fi, WPA, VPN, L2TP, IKEv2, SSTP, Always On VPN, Remote Desktop, RDP,
BitLocker, recovery key, Secure Boot, TPM, Credential Guard, LSASS, Netlogon,
Active Directory, domain controller, DNS, DHCP, SMB, certificate, authentication,
sign-in, logon, Windows Hello, Hyper-V, cluster, print, spooler,
boot, BSOD, blue screen, stop error, black screen, crash, data loss, fails to start
```

### 6.3 Default change phrases (editable)
```
changing the default, default behavior, enforce mode, now blocks, will no longer,
no longer supported, deprecat, strengthens, hardening, disabled by default,
enabled by default, now requires, audit mode
```

### 6.4 Golden test
Fixture `kb5127648.html`. Expected:
- Improvement category `Authentication`, text contains `BlockNtlmv1SSO` and `MS-CHAPv2`.
- Flagged BehaviourChange. Matched keywords include `NTLMv1`, `MS-CHAPv2`, `Wi-Fi`, `VPN`.
- Severity Red.

## 11. CI/CD

File `.github/workflows/release.yml`. Copy the pattern from `https://github.com/danrhodes/Ticktower/blob/main/.github/workflows/release.yml` (read it first, reproduce its logic).

Behaviour:
- **Push to `main`** (paths-ignore `**.md`, `docs/**`) → **pre-release**. Version `X.Y.Z-pre-release.N-<sha7>`. N counts existing `vX.Y.Z-pre-release.*` tags.
- **`workflow_dispatch`** with input `release_type` (patch / minor / major) → **full release**. Next version from the newest `vX.Y.Z` tag.
- Version lives in git tags only. Pass via `-p:Version=`.
- Runner `windows-latest`, shell `pwsh`, `fetch-depth: 0`.
- `permissions`: `contents: write`, `id-token: write`, `attestations: write`.
- `concurrency: group: release`, `cancel-in-progress: false`.
- Steps: checkout → setup-dotnet (match target framework, `10.0.x`) → `dotnet test tests/PatchRadar.Tests -c Release` → version → changelog from `git log` → publish → [full releases only: sign, section 11.2] → checksum → attest → `ncipollo/release-action@v1` → delete old pre-releases (keep 10, also delete tags).
- Name projects explicitly in commands (do not rely on solution discovery).
- Publish:
  ```
  dotnet publish src/PatchRadar -c Release -r win-x64 --self-contained true `
    -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:Version=<ver> -o publish
  ```
  Asset `PatchRadar-<tag>-win-x64.exe`. Self-contained, because Servers often lack the runtime. Also publish a framework-dependent `-slim.exe` asset (`--self-contained false`).
- Attest every asset with `actions/attest-build-provenance@v3`.
- Generate a SHA-256 file for every exe asset: `<asset>.sha256`, one line `<hash>  <filename>`. Upload with the assets. The in-app updater requires it.
- `prerelease: true` when not full. The in-app updater ignores pre-releases on the Stable channel.

### 11.1 In-app auto-update

Repo constants: owner `danrhodes`, repo `PatchRadar`, `https://github.com/danrhodes/PatchRadar`.

**Check**
- Stable channel: `GET https://api.github.com/repos/danrhodes/PatchRadar/releases/latest`. Returns newest non-draft, non-pre-release.
- PreRelease channel: `GET /releases?per_page=10`, newest including pre-releases.
- Headers: `User-Agent: PatchRadar/<ver>`, `Accept: application/vnd.github+json`. Use `ETag` / `If-None-Match`. Unauthenticated limit is 60 requests/h per IP.
- Schedule: 10 min after startup, then every `checkIntervalHours` (default 24). Manual from the tray menu.

**Versioning**
- Running version = `AssemblyInformationalVersion` with any `+sha` stripped.
- SemVer 2.0 compare. Never downgrade.
- Pre-release tags look like `X.Y.Z-pre-release.N-<sha7>`. Parse N with `-pre-release\.(\d+)-` and compare numerically. Plain SemVer string compare ranks `10-abc` below `9-abc`. That is wrong.
- `skippedVersion` is never offered again.

**Modes** (`appUpdate.mode`)
- `Off`: no checks.
- `Notify`: toast and menu item. Opens the release page.
- `Auto` (default): download, verify, apply.

**Asset selection**
- Self-contained build takes `PatchRadar-<tag>-win-x64.exe`. Slim build takes `-win-x64-slim.exe`.
- Flavour is baked at build time (`-p:UpdateFlavour=full|slim` surfaced via `AssemblyMetadata`).

**Download and verify**
- Download to `%LOCALAPPDATA%\PatchRadar\updates\<tag>\`.
- Download the matching `.sha256` asset. Compare SHA-256. Abort and log on mismatch.
- Stable channel: verify the Authenticode signature (`WinVerifyTrust`, `WINTRUST_ACTION_GENERIC_VERIFY_V2`). Require a valid chain and a signer certificate subject containing `O=SignPath Foundation`. Do not pin a thumbprint. Abort and log on failure. Gated by constant `RequireSignatureOnStable`. It stays `false` until the first signed release exists (section 11.2).
- PreRelease channel: hash check only. Pre-releases are unsigned.
- URL allowlist: `https` only. Hosts `api.github.com`, `github.com`, `objects.githubusercontent.com`, `release-assets.githubusercontent.com`. Asset URLs must come from the release JSON of this repo. Reject anything else.

**Apply** (no helper process, no elevation)
1. Wait for the single-instance mutex logic to allow handover (new process waits up to 10 s for the old one to exit).
2. Rename running `PatchRadar.exe` to `PatchRadar.exe.old`. Windows allows renaming a running exe.
3. Copy the verified exe to `PatchRadar.exe`.
4. Write `updates\pending.json`: `{ from, to, attempts: 0, healthy: false }`.
5. Start the new exe with `--post-update`. Exit the old process.
6. If the install directory is not writable, fall back to `Notify` for this version. Log it.

**Apply timing**
- `applyAutomatically: true`: apply straight after verification.
- `false`: stage, show `Restart to update to vX.Y.Z`, apply on click.
- After restart, toast `Updated to vX.Y.Z`.

**Health and rollback**
- Every start with `pending.json` present: increment `attempts`.
- Instance running 60 s: set `healthy: true`, delete `*.old`, delete `pending.json`.
- Start with `attempts >= 2` and `healthy: false`: restore `PatchRadar.exe.old`, set `skippedVersion` to the failed version, toast `Update vX failed, rolled back`, log.

**Install location**
- Recommend `%LOCALAPPDATA%\Programs\PatchRadar\PatchRadar.exe` (per-user, writable). Document in README. Program Files needs elevation: updater falls back to Notify there.

**Integrity limits (state plainly in README)**
- The `.sha256` file sits in the same release. It catches corruption and bad downloads. It does not stop a compromised repo or token. On Stable, the Authenticode check covers that once enforced: only SignPath-approved builds carry the signature.
- Stronger check: GitHub build attestation. Verify manually with `gh attestation verify <exe> --repo danrhodes/PatchRadar`.
- Full releases are Authenticode-signed via SignPath Foundation (section 11.2). Pre-releases are unsigned. SmartScreen reputation still builds over time.

### 11.2 Code signing (SignPath Foundation)

Scope: **full releases only** (manual workflow run). Pre-releases stay unsigned. Reason: Foundation signing policies are expected to need manual approval per request (**unverified** for this project). Signing every push to `main` would block on approval.

Publisher shown to users: `SignPath Foundation`. The private key stays in SignPath's HSM.

**Human steps (Dan, not Claude Code)**
1. Apply to the SignPath Foundation OSS programme. Use the Apply link on `signpath.org`. Check the current page, two URL variants exist in the wild. Reported lead time about 1 week (**unverified**).
2. Enable MFA on the GitHub account and the SignPath account. Foundation terms require MFA for all team members.
3. After approval, in the SignPath web app create:
   - Project slug `patchradar`.
   - Signing policy slug `release-signing`.
   - Artifact configuration: ZIP containing both exes, PE signing for each (reference copy in `docs/signpath/artifact-configuration.xml`).
   - Trusted build system: GitHub, linked to `danrhodes/PatchRadar`.
   - Approver: Dan.
4. Add to the GitHub repo: secret `SIGNPATH_API_TOKEN`, variable `SIGNPATH_ORGANIZATION_ID`.

**Foundation conditions to meet (verify against current terms at apply time)**
- OSI-approved licence (MIT qualifies). Public repo. No proprietary components.
- Signing team = development team. Roles assigned (Author, Approver).
- Published code signing policy. Attribution text on the project page.
- Privacy statement covering network use.
- Foundation checks project reputation and control. A new repo may need history. See risks.

**Repo content Claude Code builds**
- README section `Code signing policy`:
  - Attribution line: `Free code signing provided by SignPath.io, certificate by SignPath Foundation.`
  - Roles: Author and Approver = `danrhodes`.
  - Verify instruction: `Get-AuthenticodeSignature .\PatchRadar.exe`. Signer must be SignPath Foundation.
  - Privacy statement: no telemetry. Network contact only with `support.microsoft.com`, `learn.microsoft.com` and GitHub.
- `.signpath/policies/patchradar/release-signing.yml`. Write to the format at `https://docs.signpath.io/trusted-build-systems/github`. Restrict to repo `danrhodes/PatchRadar`, workflow `release.yml`, branch `main`. Disallow reruns if the option exists.
- `docs/signpath/artifact-configuration.xml` (reference copy only).

**Workflow order (full releases, `if: steps.v.outputs.full == 'true'`)**
1. Publish both exes to `publish/`.
2. Zip them into `unsigned/PatchRadar-unsigned.zip`. Original exe names inside.
3. `actions/upload-artifact@v4`, step id `upload-unsigned`.
4. Submit signing request:
   ```yaml
   - uses: signpath/github-action-submit-signing-request@v2   # verify current major
     with:
       api-token: ${{ secrets.SIGNPATH_API_TOKEN }}
       organization-id: ${{ vars.SIGNPATH_ORGANIZATION_ID }}
       project-slug: patchradar
       signing-policy-slug: release-signing
       artifact-configuration-slug: <name from SignPath>
       github-artifact-id: ${{ steps.upload-unsigned.outputs.artifact-id }}
       wait-for-completion: true
       wait-for-completion-timeout-in-seconds: 3600
       output-artifact-directory: signed
   ```
   Verify input names against the action's `action.yml` before use.
5. Unzip `signed/` over `publish/`.
6. Verify: `Get-AuthenticodeSignature` on each exe. Fail the job unless `Status` is `Valid` and the signer subject contains `SignPath Foundation`.
7. Generate `.sha256` files **after** signing. Signing changes the hash.
8. Attest the signed exes with `actions/attest-build-provenance@v3`.
9. Create the release.

Constraints:
- Every job before the signing request must run on GitHub-hosted runners. `windows-latest` complies.
- The runner stays occupied while waiting for approval. Timeout 60 min. If it expires, re-run the workflow.
- Pre-release path unchanged: unsigned exe, hash, attest, release. Release notes state `Unsigned pre-release`.

**Updater enforcement rollout**
1. Ship with `RequireSignatureOnStable = false`.
2. Publish the first signed full release. Confirm `Get-AuthenticodeSignature` shows Valid on a clean machine.
3. Set the constant to `true` in the next commit. Earlier unsigned Stable releases then fail the check by design.

## 12. Testing

- Parser: fixtures for at least 6 KBs: Windows 11 cumulative (with known issues), Windows 11 cumulative (no issues), Server 2025, Server 2022, Server 2016, one .NET Framework KB. Add KB5127648 as golden.
- Severity engine: table-driven tests for every rule in section 6, including Resolved and BehaviourChange.
- Keyword matcher: word boundary, regex prefix, case.
- Settings: round-trip, corrupt file recovery, unknown key preservation, default fill.
- Merger: WUA + QFE dedupe, uninstall handling, failed installs, category and regex filters.
- Cache: TTL logic, backoff schedule.
- App updater: version comparer (including pre-release N numeric order), asset picker (full vs slim), SHA-256 verification, Authenticode verifier (behind an interface, fake in tests: valid, unsigned, wrong signer, tampered), URL allowlist, `pending.json` rollback state machine, mode behaviour (Off, Notify, Auto), non-writable directory fallback. Use fakes for HTTP and file system.
- No test may hit the network.
- Manual test matrix (record in `tracker.md`): Windows 11, Server 2016, 2019, 2022, 2025. Standard user and admin.

## 13. Security and privacy

- Outbound traffic only to `support.microsoft.com`, `learn.microsoft.com`, and GitHub (`api.github.com`, `github.com`, `objects.githubusercontent.com`, `release-assets.githubusercontent.com`) for app updates. No telemetry.
- No admin rights. No services. No scheduled tasks.
- Treat all fetched HTML as untrusted. Parse to text. Never render remote HTML or run its scripts. Detail window shows plain text only.
- Validate and sanitise URLs before opening. Allow only `https` on Microsoft hosts for the KB link.
- Stable-channel updates install only exes with a valid SignPath Foundation Authenticode signature, once `RequireSignatureOnStable` is enabled.
- Proxy credentials not stored. Use default system proxy unless `network.proxy` is set.

## 14. Non-goals

- Installing, uninstalling or hiding updates.
- Windows 10 support.
- Fleet or RMM reporting.
- Localisation.
- Updating via service, MSI, winget or Intune. The updater is per-user and in-process.
